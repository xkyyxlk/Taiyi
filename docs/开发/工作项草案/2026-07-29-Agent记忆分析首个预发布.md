## 背景

Agent 长期记忆分析首个里程碑已经完成框架无关 JSONL 协议、确定性变化与治理规则、
版本化策略、三种报告、LangGraph/LangSmith 参考适配器、分层模拟和性能预算，并已合入
`main`。当前可安装发布版本仍是 `v0.1.1`，其产品中心和包元数据仍描述身份演化原型。

新分析能力增加了新的用户、命令入口、协议、报告和持续集成用途，超过 `0.1.1` 维护修订的
范围，适合进入 `0.2` 版本线。但当前证据只证明工程正确性，尚未经过真实 Agent 项目验证，
不能把首个公开构建标记为稳定正式版，也不能暗示实际采用价值已经得到验证。

## 版本与发布结论

### 首个预发布

- Python 包版本使用 PEP 440 形式 `0.2.0a1`；
- Git 标签和 GitHub Release 使用人类可读形式 `v0.2.0-alpha.1`；
- GitHub Release 必须标记为预发布，不得标记为正式稳定版本；
- Release 附加源码包、wheel、SHA-256 校验清单和中文发布说明；
- 首个预发布不进入 PyPI，避免在真实项目验证前形成默认稳定安装预期；
- 安装方式以下载固定 Release 附件后本地 `pip install` 为准。

### 后续版本

- 预发布后的兼容修复使用 `0.2.0a2`、`0.2.0a3`，相应
  Git 标签分别为 `v0.2.0-alpha.2`、`v0.2.0-alpha.3`；
- 不覆盖既有标签或附件，不在原版本号下替换构建产物；
- 真实项目影子验证完成并满足独立验收标准后，再决定是否发布 `0.2.0` 正式版；
- 如果真实验证要求破坏性调整协议或产品边界，继续发布新的预发布版本，不为追求版本号
  提前进入正式版。

### 独立版本边界

- 工具包版本、JSONL 协议版本、报告版本、规则版本和策略版本分别管理；
- `0.2.0a1` 继续发布当前 JSONL 协议 `1.0`，包版本提升不自动改变协议版本；
- 当前 `1.0` 字段、枚举和含义不得因发布整理原地改变；
- 兼容新增协议字段必须先定义读取行为和测试，再提升协议次版本；
- 删除字段、改变含义或收紧既有合法输入必须提升协议主版本并提供迁移说明。

## 目标

- 把已经合入的 Agent 记忆分析能力构建为可下载、可校验、可独立安装的 Alpha 预发布；
- 让包元数据、README、变更日志、产品状态和发布说明准确描述新产品方向；
- 保持 `v0.1.1` 身份演化命令、SQLite 数据和本地产品原型兼容；
- 对分析命令、旧模块、构建产物和全新环境安装提供可复核验证证据；
- 明确披露尚无真实项目价值、接入成本或误报成本证据；
- 建立不可变标签、附件、哈希、发布说明和永久迭代记录。

## 非目标

- 不在本工作项开展真实项目影子验证或宣称真实项目价值；
- 不把 GitHub 预发布同步到 PyPI；
- 不增加新的分析规则、协议字段、框架适配器或产品功能；
- 不进行大模型语义冲突、事实过期或攻击意图裁决；
- 不自动写入、修复、晋升或回滚外部记忆库；
- 不迁移、重写或删除 `v0.1.1` 身份 SQLite 数据；
- 不建设托管服务、团队权限或新的网页产品；
- 不为减小安装体积拆分 Python 包或调整现有运行依赖。

## 发布内容

### 用户能力

- `taiyi analyze validate`：校验版本化 JSONL；
- `taiyi analyze check`：运行确定性变化、规则和策略分析；

- `simulate`、`simulate-malformed`、`simulate-milestone` 和 `benchmark`；
- `adapt-langgraph` 离线参考适配器；
- 当前 `v0.1.1` 身份演化命令和本地产品原型兼容能力。

### 构建产物

- wheel 安装包 `taiyi_ai-0.2.0a1-py3-none-any.whl`；
- 源码包 `taiyi_ai-0.2.0a1.tar.gz`；

本地数据库、环境文件、API 密钥、模拟输出目录或临时报告。

- 旧身份 SQLite 不迁移、不初始化于分析命令、不改变表结构；
- 原有身份、同位体、来源、人工审核、不可变快照、回滚和擦除语义保持不变；
- 新分析命令默认离线，不调用模型或网络，不获得外部记忆库写权限；
- 报告继续只保存最小必要证据，不复制原始事件或记忆正文；
- JSONL 协议 `1.0`、规则编号、退出码和策略语义不得为发布整理而改变；
- Python 最低版本继续为 `3.11`，现有 `3.11`、`3.12`、`3.13` 支持矩阵不变；
- `taiyi-ai` 包名和 `taiyi` 命令入口不变，现有用户无需迁移数据或更换命令名。

## 建议发布流程

1. 维护者分配正式 `TY-<数字>`，建立 GitHub 议题并创建规范功能分支；
2. 更新版本、包元数据、变更日志、README、产品状态和发布文档；
3. 运行常规完整检查、万级里程碑模拟和最大档性能预算；
4. 从干净工作树构建源码包和 wheel，检查内容与元数据；
5. 在全新 Python `3.11`、`3.13` 环境安装 wheel 并执行新旧命令冒烟；
6. 冻结发布说明、检查清单、产物哈希和最终提交；
7. 将功能分支审核并合入 `main`，在主干重新运行完整验证和构建；
8. 优先创建签名注释标签 `v0.2.0-alpha.1`；没有可用签名条件时，必须由维护者明确接受
   未签名注释标签并记录原因；
9. 推送标签，创建标记为预发布的 GitHub Release，附加源码包、wheel 和哈希清单；
10. 从 Release 重新下载并复核附件、哈希、安装与冒烟；
11. 更新正式议题、迭代状态和发布记录，保持工作树与远端主干一致。

## 失败与替代策略

- 发布前任一工程、性能、构建或安装检查失败时停止发布，修复后重新生成全部产物；
- 发布后发现缺陷时不移动标签、不覆盖附件，使用 `0.2.0a2` 发布修复；
- 发现安全或数据破坏风险时在 Release 顶部增加明确警告并停止推荐下载，同时建立独立修复
  工作项；是否删除公开附件必须由维护者单独决定；
- 用户需要稳定旧功能时可以继续安装 `v0.1.1`；`0.2.0a1` 不得迁移或改变由旧版本创建的
  身份数据，跨版本复核前应先备份并使用独立环境；
- 如果 GitHub Release 无法完成，不以临时网盘、聊天附件或未经记录的构建替代正式发布。

## 风险与缓解

| 风险 | 影响 | 缓解方式 |
|---|---|---|
| Alpha 被误认为稳定版本 | 用户过早用于生产阻断 | 使用 `0.2.0a1`、GitHub 预发布标记和显著边界说明 |
| 包版本与协议版本混淆 | 用户错误推断协议兼容性 | 在报告、README 和发布说明中分别列出工具与协议版本 |
| 新旧产品共存造成认知混乱 | 用户不知道默认能力和数据边界 | 元数据优先介绍分析工具，单列 `v0.1.1` 兼容模块 |
| GitHub-only 降低安装便利性 | 早期用户需要手动下载 | 提供固定附件、哈希和清晰安装命令，正式版再评估 PyPI |
| 未经真实项目验证 | 无法证明接入和发现价值 | 明确 Alpha 证据边界，正式版前另建影子验证工作项 |
| 依赖仍包含旧模块运行库 | 分析用户安装体积较大 | 本次保持单包兼容，不在发布工作项中引入拆包风险 |
| 标签或附件被覆盖 | 发布证据不可复核 | 标签和附件不可变，缺陷通过新的 Alpha 版本修复 |
| 构建环境差异 | 本地通过但用户无法安装 | 在 Python 支持矩阵端点执行全新环境安装和重新下载冒烟 |
