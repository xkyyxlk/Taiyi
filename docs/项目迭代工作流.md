# 太一项目迭代工作流

## 1. 目标

这套工作流用于支持太一长期、连续、开放地迭代，并解决以下问题：

- 工作不会只存在于某次聊天记录中；
- 新会话能在几分钟内恢复当前上下文；
- 多位贡献者和多个会话不会互相覆盖；
- 每次身份、存储或协议变更都能追溯其原因；
- 任意版本都能说明完成内容、验证结果和已知风险。
- 当前状态滚动更新后，仍能逐次回看每个历史迭代。

## 2. 项目事实来源

发生信息冲突时，按以下优先级判断：

1. 当前工作区、Git 分支、提交和差异，代表实际代码状态；
2. 自动测试、静态检查和可复现实验，代表已经验证的行为；
3. `docs/迭代状态.md`，代表当前意图、断点和下一步；
4. `docs/迭代记录/`，代表每次迭代的目标、改动、验证和遗留事项；
5. GitHub 议题、合并请求和 `docs/adr/`，代表需求、审核和决策历史；
6. 聊天记录只用于补充语境，不作为唯一事实来源。

任何重要信息如果只出现在聊天中，都必须在会话结束前写入上述仓库文件。

## 3. 持久化协作文件

| 文件或系统 | 用途 | 更新时机 |
|---|---|---|
| `AGENTS.md` | 长期稳定的协作约束 | 出现反复错误或流程变化时 |
| `docs/迭代状态.md` | 当前里程碑、工作项、断点和下一步 | 每次开始、暂停或完成工作时 |
| `docs/迭代记录/记录索引.md` | 永久保存每次迭代及其入口 | 每次产生仓库改动的迭代结束时 |
| `docs/迭代记录/迭代记录模板.md` | 统一历史记录结构 | 归档字段变化时 |
| `docs/会话交接模板.md` | 统一交接格式和新会话提示词 | 交接字段变化时 |
| GitHub 议题 | 单项需求、验收标准、非目标和依赖 | 工作项立项及范围变化时 |
| `docs/adr/` | 难以逆转的架构和协议决策 | 决策被接受或替换时 |
| 合并请求 | 改动、风险、测试和审核记录 | 准备合入主分支时 |
| `变更日志.md` | 面向用户的版本变化 | 准备发布时 |

`docs/迭代状态.md` 只保留当前现场和最近完成事项，避免状态文件无限增长；每次迭代的
工程细节永久保存在 `docs/迭代记录/`，并通过 Git、议题、合并请求和架构决策记录补充
证据。变更日志面向使用者，不能替代工程迭代档案。

### 3.1 迭代档案规则

- 每次产生仓库改动的开发迭代建立一份记录；没有仓库改动的纯讨论可以不建档；
- 一个跨会话工作项可以保留多份会话记录，并在完成时增加一份工作项总结；
- 新记录从模板复制，使用 `年-月-日-序号-主题.md` 命名，并追加到索引末尾；
- 记录必须包含目标、完成内容、重要决策、验证结果、相关提交、影响范围和遗留事项；
- 已完成记录只追加、不删除、不覆写，纠错时在原记录末尾追加日期、内容和依据；
- 历史回填必须明确标注，无法从 Git 或测试证明的细节不得猜测。

## 4. 工作项定义

每项工作使用 `TY-<数字>` 编号。开始编码前至少明确：

- 背景与问题；
- 本次目标；
- 明确非目标；
- 可验证的验收标准；
- 影响的身份不变量和安全边界；
- 数据迁移与兼容性；
- 测试计划；
- 依赖、风险和阻塞条件。

范围尚不明确的想法先进入讨论，不直接进入开发。

## 5. 工作项状态

```text
待整理 -> 可开发 -> 开发中 -> 待审核 -> 已合入 -> 已发布
                    \-> 已阻塞
                    \-> 已取消
```

- 待整理：只有想法，尚无完整验收标准；
- 可开发：范围、依赖和验收标准已明确；
- 开发中：已有负责人和分支；
- 待审核：实现完成且本地验证通过；
- 已合入：已进入 `main`，尚未随版本发布；
- 已发布：已经包含在正式版本中；
- 已阻塞：明确记录阻塞原因和解除条件。

## 6. 标准迭代流程

### 6.1 规划

1. 从路线图或用户反馈创建 GitHub 议题；
2. 指定 `TY-<数字>` 编号、目标、非目标和验收标准；
3. 判断是否需要架构决策记录、数据库迁移或安全评审；
4. 将工作项标记为“可开发”；
5. 在 `docs/迭代状态.md` 中登记当前工作项。

### 6.2 启动

1. 确认 `main` 干净且已经同步；
2. 创建 `codex/ty-<编号>-<主题>` 分支；
3. 阅读相关代码、测试、议题和架构决策记录；
4. 先运行与改动相关的基线测试；
5. 把第一项具体操作写入状态文件。

不得在有不明未提交改动时切换分支、重置工作区或开始另一项任务。

### 6.3 实现

1. 将工作拆成可以单独验证的小步骤；
2. 先保护不变量，再实现正常功能；
3. 每步同步补充测试、迁移和中文文档；
4. 每完成一个稳定检查点就创建提交；
5. 范围或设计发生变化时先更新议题或架构决策记录；
6. 随时维护 `docs/迭代状态.md` 中的完成项和下一步。
7. 在本次迭代记录中同步积累实际完成内容和验证证据。

### 6.4 验证

常规完整验证命令：

```bash
ruff format --check .
ruff check .
mypy src/taiyi
pytest
```

根据改动类型增加验证：

- 存储变更：旧数据库升级、事务中断和回滚测试；
- 归一变更：来源、审核门、快照不可变和陈旧提案测试；
- 删除变更：数据库、索引、导出和模型上下文残留测试；
- 模型提供器变更：离线模拟测试和可选真实接口冒烟测试；
- 命令行变更：帮助文本、退出码和端到端工作流测试；
- 文档变更：中文规范和本地链接检查。

### 6.5 审核与合入

1. 创建合并请求并关联工作项；
2. 描述行为变化、数据迁移、风险和验证证据；
3. 确认持续集成全部通过；
4. 审核来源追溯、隔离、人工审核、不可变和删除不变量；
5. 解决审核意见后再次运行相关测试；
6. 合入 `main` 后更新工作项、迭代状态和本次迭代记录。

### 6.6 发布

1. 按语义化版本确定版本号；
2. 更新 `变更日志.md`、安装说明和已知限制；
3. 从全新环境安装构建产物并运行标准实验；
4. 创建签名标签；
5. 发布软件包和版本说明；
6. 将已包含的工作项标记为“已发布”；
7. 在 `docs/迭代状态.md` 中切换到下一里程碑。
8. 确认该版本包含的所有迭代记录都已归档，并据此整理变更日志。

## 7. 新会话如何继续工作

### 7.1 结束旧会话前

按 `docs/会话交接模板.md` 更新 `docs/迭代状态.md`，至少记录：

- 当前分支和工作项；
- 已完成且经过验证的内容；
- 尚未完成的内容；
- 下一条可以直接执行的操作；
- 未提交文件和修改原因；
- 最近执行的验证及结果；
- 已知风险、阻塞和待用户决定事项。

如果本会话产生了仓库改动，还要从迭代记录模板创建记录、追加索引，并写明当前检查点
提交。工作尚未完成时记录状态为“已暂停”，下一会话不得覆盖这份记录，而应建立新的
会话迭代记录。

未完成实现应在功能分支创建明确的检查点提交。不要把半成品提交到 `main`。如果暂时
不能提交，必须保留同一工作区，并在状态文件中列出未提交文件。

### 7.2 启动新会话

新会话应打开同一个仓库和正确分支，然后使用以下提示词：

```text
继续开发太一项目。开始前请依次阅读 AGENTS.md、README.md、
docs/项目迭代工作流.md、docs/迭代状态.md、docs/迭代记录/记录索引.md，
以及状态文件引用的最近迭代记录、议题和架构决策记录。
随后检查 git status --short --branch 和 git log -5 --oneline。
请从“下一步操作”继续，不要重做已完成事项，不要覆盖已有未提交改动。
完成或暂停前，运行约定验证，新增本次迭代记录并更新 docs/迭代状态.md。
```

如果 Codex 已自动载入 `AGENTS.md`，仍应主动读取迭代状态，因为状态内容会频繁变化。

### 7.3 意外中断后的恢复

如果旧会话来不及交接，新会话按以下顺序恢复：

1. 检查当前分支、`git status`、`git diff` 和最近提交；
2. 阅读 `docs/迭代状态.md`、迭代记录索引、最近相关记录和议题；
3. 运行最小相关测试，判断现场是否处于可运行状态；
4. 对比状态文件与实际差异，列出已经完成、部分完成和未开始内容；
5. 先修正状态文件，再继续编码；
6. 不确定改动归属时停止修改并向用户确认，不得清理现场。

## 8. 多会话并行

- 一个工作项只由一个主分支负责；
- 每个并行会话使用独立分支和独立工作树；
- 不让两个会话同时修改同一工作树；
- 公共接口或数据结构先通过架构决策记录达成一致；
- 子任务完成后通过提交或合并请求交付，不通过聊天复制大段代码；
- 合并前重新同步 `main` 并运行完整验证。

## 9. 完成定义

工作项只有同时满足以下条件才算完成：

1. 验收标准全部满足；
2. 新行为具有自动测试；
3. 原有身份与安全不变量保持成立；
4. 数据迁移、兼容性和删除语义已经处理；
5. 文档、帮助文本和变更日志已按需更新；
6. 完整检查通过；
7. 议题、合并请求和 `docs/迭代状态.md` 已同步；
8. 本次迭代记录已归档并追加到索引；
9. 没有未说明的临时文件、调试代码或未提交改动。

## 10. 流程维护

当同类交接或实现错误重复发生时，应进行简短复盘，并更新 `AGENTS.md`、本工作流或
模板。流程本身也采用小步修改、审核和版本追踪，不依赖口头约定。
